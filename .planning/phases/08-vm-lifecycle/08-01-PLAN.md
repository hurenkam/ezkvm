<objective>

Replace `src/main.rs`'s hardcoded demo script with a real `clap`-driven CLI (`ezkvm <start|stop|kill|reset|status> <vm-name>`) and wire the thinnest possible end-to-end "start" path: load `host.yaml`, resolve `<vm-name>.yaml`, build a `Runtime`, render the Phase-7 `QemuCommandLine` with a `-qmp` flag appended, spawn `qemu-system-x86_64` as a detached process, and persist a `VmHandle` state file. This is the phase's tracer bullet — it touches every layer (CLI, host config, VM config, Runtime, QEMU cmdline, process spawn, state persistence) on the simplest possible case (no TPM, no UI client) so later plans (swtpm readiness, QMP stop/kill/reset, UI-client launch) extend a proven, already-running path instead of an unproven one.

Purpose: Prove the full CLI-to-child-process-to-state-file architecture works before adding TPM readiness polling, QMP control, and UI-client launch on top of it (D-01 through D-10, D-16).

Output: A working `ezkvm start <vm-name>` / `ezkvm status <vm-name>` pair against a TPM-less VM config, backed by real detached child-process spawning and a real YAML state file, plus `host.yaml` loading and `<vm-name>` input validation.

**Test independence note:** Per the project's cross-distro deployment goal, none of this phase's tests spawn the real `qemu-system-x86_64`/`swtpm`/UI-client binaries or assume any particular Linux distribution's tooling is installed. Instead, this plan introduces `src/bin/fake_qemu.rs` — a trivial, host-independent stub binary compiled by the same `cargo build`/`cargo test` invocation as `ezkvm` itself, standing in for `qemu-system-x86_64` in every test. Tests reference it via `env!("CARGO_BIN_EXE_fake_qemu")` and configure it as `HostConfig.qemu_path`, so the entire test suite passes identically on Debian, Ubuntu, Fedora, or any other distribution the Rust toolchain targets. Real-binary, real-distro verification (actually installing `qemu-system-x86_64`/`swtpm`/`looking-glass-client` on a target Debian 13 / Ubuntu 26.04 image) is explicitly deferred to Phase 10 ("Deployment Packaging - Debian/Ubuntu").

</objective>

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI argument -> filesystem path | `<vm-name>` is attacker-influenceable (anyone who can invoke the `ezkvm` binary) and is joined into a filesystem path (`vm_dir.join(...)`, `state_dir.join(...)`) |
| `ezkvm` process -> spawned children | qemu/swtpm/UI-client processes and their Unix sockets are local-host trust boundaries between the invoking user and other local users on a multi-user host |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-8-01 | Tampering / Information Disclosure | `HostConfig::resolve_vm_name` / `vm_yaml_path` | high | mitigate | Reject `<vm-name>` values containing `/`, `..`, or an absolute-path prefix before any `PathBuf::join` call (Task 1, Task 2) |
| T-8-02 | Tampering | `VmHandle::write` state file | medium | mitigate | State file lives inside a `0700` directory (T-8-03's mitigation covers this too); no additional symlink-following logic is added in this plan since the directory-permission mitigation already prevents another local user from placing a symlink there in the first place |
| T-8-03 | Elevation of Privilege / Denial of Service | `state_dir` (holds `VmHandle` state file and, from later plans, QMP/swtpm sockets) | high | mitigate | `process::ensure_dir_secure` creates `state_dir` with `0700` permissions before any state file or socket is written into it (Task 1) |

</threat_model>
