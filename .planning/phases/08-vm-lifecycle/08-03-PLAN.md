<objective>

Implement the QMP (QEMU Machine Protocol) client and wire it into the `stop`, `kill`, and `reset` CLI verbs stubbed out (as `todo!()`) by `08-01`'s tracer. This plan touches `src/main.rs` only to replace the three `todo!()` match-arm bodies with real calls into new `lifecycle::stop`/`kill`/`reset` modules — it does not touch `lifecycle::start`/`readiness`/`ui_client`, so it executes in parallel with `08-02` (which extends `start()` in place), both depending only on `08-01`'s tracer.

Purpose: Fulfil D-18 through D-21 and VMGR-03/04/05 — graceful shutdown, force-stop, and reset of a running VM entirely over its QMP Unix socket, with the exact EOF-tolerance and fire-and-forget nuances the QMP spec requires.

Output: `ezkvm stop|kill|reset <vm-name>` all work against a running qemu process's QMP socket, and `stop`/`kill` also clean up the tracked UI-client process and the state file on success.

**Test independence note:** This plan's Task 1 already correctly uses a test-local `UnixListener`-based fake QMP server (no real binary involved) and needs no change. Task 2's tests reuse `08-01`'s `src/bin/fake_qemu.rs` stub (via `env!("CARGO_BIN_EXE_fake_qemu")`) as the "qemu" process whose QMP socket is exercised — `fake_qemu` implements the minimal QMP responder (handshake, `system_powerdown`/`quit` exit, `system_reset` no-op) needed for these tests, including an `FAKE_QEMU_IGNORE_POWERDOWN` env-var mode that simulates a guest that never shuts down, for the escalation-timeout tests (Test 5/6). No real `qemu-system-x86_64` binary is spawned anywhere in this plan.

- **Test 3:** Against a fake server, sending a raw `system_powerdown` request *before* the client-internal `qmp_capabilities` handshake is never observable from outside — assert (by inspecting the fake server's received-message log) that `qmp_capabilities` is always the first command byte-sequence sent, before any real command, for every `QmpClient::connect` + `.system_powerdown()` call sequence.
- **Test 4:** Against a fake server that responds normally to `qmp_capabilities` but then closes the connection immediately (no response) when it receives a `quit` request, `client.quit()` returns `Ok(())`, not an `Err` — the EOF-as-success behavior from Pitfall 4.
- **Test 5:** Against a fake server, `client.system_reset_fire_and_forget()` returns `Ok(())` immediately after writing the request, without attempting to read any response at all (assert by having the fake server never write a response for `system_reset` and confirming the call still completes and returns quickly, well under any read-timeout).
- **Test 6:** Against a fake server that returns `{"error": {"class": "CommandNotFound", "desc": "..."}}` for `system_powerdown`, `client.system_powerdown()` returns `Err(QmpError::CommandFailed { .. })` with the description preserved.

</behavior>

- **Test 2:** `lifecycle::kill::kill(host_config, vm_name)` against a spawned `fake_qemu` process sends `quit` and results in the process no longer being alive shortly afterward, regardless of whether a QMP response was received (Pitfall 4).
- **Test 3:** `lifecycle::reset::reset(host_config, vm_name)` against a spawned `fake_qemu` process sends `system_reset` and returns `Ok(())` promptly (well under 1 second), without waiting for or requiring any QMP response, and the `fake_qemu` process remains alive afterward (a reset does not terminate the process — `fake_qemu` is designed to no-op on `system_reset`).
- **Test 4:** After a successful `kill()` against a test VM that also has a tracked `ui_client_pid` (spawn a `fake_ui_client` instance, from `08-02`'s `src/bin/fake_ui_client.rs`, and record its PID in the `VmHandle` before calling `kill`), the UI-client PID is no longer alive after `kill()` returns, and `VmHandle::read()` returns `None` (state file removed) — D-20 in full.
- **Test 5:** With `stop_escalation_timeout_secs` unset (default), `stop()` against a `fake_qemu` process started with `FAKE_QEMU_IGNORE_POWERDOWN=1` (so it acknowledges `system_powerdown` but never exits) blocks indefinitely rather than auto-sending `kill` — test this with a bounded wait-with-timeout in the *test* itself (not in `stop()`) that asserts no `quit` was ever sent within a short window, then cleans up the process directly.
- **Test 6:** With `stop_escalation_timeout_secs` set to a short value (e.g. 1s) in `HostConfig`, `stop()` against the same `FAKE_QEMU_IGNORE_POWERDOWN=1` `fake_qemu` process falls back to sending `quit` after that timeout elapses (`fake_qemu` always exits on `quit`, regardless of the ignore-powerdown flag).

</behavior>

<action>

- Create `src/lifecycle/stop.rs`: `pub fn stop(host_config: &HostConfig, vm_name: &str) -> Result<(), LifecycleError>` — read the `VmHandle` (error if absent/stale), connect a `QmpClient` to `qmp_socket_path`, call `system_powerdown()`, then block waiting for `is_pid_alive(qemu_pid)` to become `false` via a poll loop (short interval, e.g. 200ms) — indefinitely by default (D-18). If an escalation timeout is configured (via `host_config.stop_escalation_timeout_secs()` or a CLI-supplied override passed as a parameter, D-19), and the qemu PID has not exited by that deadline, reconnect (or reuse the same client if still open) and send `quit` instead of continuing to wait indefinitely. On confirmed exit, terminate the tracked `ui_client_pid` if present (D-20) and call `VmHandle::remove`.
- Create `src/lifecycle/kill.rs`: `pub fn kill(host_config: &HostConfig, vm_name: &str) -> Result<(), LifecycleError>` — read the `VmHandle`, connect, call `quit()` (already EOF-tolerant per Task 1), wait briefly for `is_pid_alive` to become false (bounded wait with a fallback `terminate_pid(qemu_pid, true)` SIGKILL if `quit` alone did not result in exit within a short grace period — a defensive fallback, not the primary mechanism, since VMGR-04's requirement text explicitly allows a "SIGTERM fallback"), terminate the tracked `ui_client_pid` if present (D-20), and `VmHandle::remove`.
- Create `src/lifecycle/reset.rs`: `pub fn reset(host_config: &HostConfig, vm_name: &str) -> Result<(), LifecycleError>` — read the `VmHandle`, connect, call `system_reset_fire_and_forget()`, return `Ok(())` immediately (D-21) — no state-file mutation, no UI-client termination (the VM is still running after a reset).
- Add a `LifecycleError` (thiserror) shared by `stop`/`kill`/`reset` wrapping `VmHandleError`, `QmpError`, and a `NotRunning` variant for when no live `VmHandle` is found.
- Edit `src/main.rs`: replace the three `todo!()` bodies in the `Verb::Stop`/`Verb::Kill`/`Verb::Reset` match arms with calls to `lifecycle::stop::stop`, `lifecycle::kill::kill`, `lifecycle::reset::reset` respectively; add a `--escalate-after <secs>` flag to the `Stop` subcommand's clap definition (D-19's per-invocation override, taking precedence over `host.yaml`'s `stop_escalation_timeout_secs` when both are present).

</action>

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local user -> QMP Unix socket | Any local process able to connect to the QMP socket path can issue `system_powerdown`/`quit`/`system_reset` against that VM — QMP itself has no authentication layer |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-8-06 | Elevation of Privilege / Denial of Service | QMP Unix socket (created by qemu inside `08-01`'s `0700` `state_dir`) | high | mitigate | No additional QMP-level auth exists to lean on (matches libvirt/qemu's own local-socket trust model); this plan relies entirely on `08-01`'s `state_dir` `0700` permission mitigation (T-8-03) — verified here by a test asserting the QMP socket's containing directory is still `0700` after `stop`/`kill`/`reset` run |
| T-8-07 | Denial of Service | `quit`'s EOF-as-success handling | low | accept | Treating EOF as success (per the QMP spec's own documented behavior) cannot be abused to falsely report a kill succeeded when it did not, since `kill()`'s implementation independently confirms via `is_pid_alive` polling rather than trusting the QMP response alone |

</threat_model>
