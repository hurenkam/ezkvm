<objective>
Generalize the single hardcoded `PvScsi` Runtime struct into a `GenericScsiController` parameterized
by a `controller_type: ScsiControllerType` field (`PvScsi` | `VirtioScsiPci`), per D-02. Today,
`self.vm_conf.scsihw` is parsed by the Proxmox importer but discarded — every SCSI disk becomes a
`PvScsi` controller regardless of the real `scsihw` value, silently losing information for the
majority of real corpus VMs (only `felucia/108.conf` uses `pvscsi`; every other corpus file surveyed
uses `virtio-scsi-pci` or `virtio-scsi-single`).

This plan covers the shared-bus controller types only (`pvscsi`, `virtio-scsi-pci` — structurally
identical, differing only in the emitted QEMU device-model string, per D-02). `virtio-scsi-single`
(D-03's separate per-disk merged device) is explicitly deferred to Plan 08.1-03 — do NOT add a third
`ScsiControllerType` variant for it here (D-03 LOCKED anti-pattern).

Depends on Plan 08.1-01 (wave 1) because both plans touch the same 5 shared conversion-layer files
(`importer.rs`, `error.rs`, `runtime/parser.rs`, `runtime/builder.rs`, `runtime/q35.rs`) — sequencing
avoids merge conflicts on the same exhaustive-match sites.

Per D-07/Research Pitfall 3/Open Question 1: `PciBusDeviceKind::PvScsi` and `IsaBusDeviceKind::PvScsi`
(vestigial, zero schema/handler wiring today, unneeded by any corpus) are explicitly left AS-IS in
this plan — their variant names stay literally `PvScsi` (not renamed), and no new PCI-bus or ISA-bus
schema/handler wiring is added. Only `PcieBusDeviceKind::PvScsi` (the actively-used, PCIe-only real
path) is renamed to `ScsiController`.

Purpose: Satisfy RUNT-11 (partially — pvscsi/virtio-scsi-pci variants; virtio-scsi-single follows in
Plan 08.1-03) — SCSI controller type is a first-class Runtime field, not silently discarded.
Output: `GenericScsiController` with a real `controller_type`; `coruscant/100.conf` (`virtio-scsi-pci`)
importable and emitting the correct device model for the first time.
</objective>
