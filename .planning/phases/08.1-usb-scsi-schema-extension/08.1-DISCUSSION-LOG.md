# Phase 8.1 Discussion Log

**Trigger**: During review of Phase 9's plan-checker result, the user rejected the handler-level
USB workaround planned in `09-02-PLAN.md` and flagged a second issue (SCSI controller type
collapsed to `pvscsi`), requesting proper schema-level fixes in both Runtime and the ezkvm YAML
schema instead of point-fixes. Decided to split this into a new inserted phase (8.1) before Phase
9, keeping Phase 9 as pure round-trip verification.

**Round 1 — USB identity representation**

Explored `src/config/qemu/handlers/usb.rs` (panic site), `src/runtime/devices/usb_generic.rs`,
`src/config/ezkvm/schema/usb.rs`, and the Proxmox importer's USB import loop — confirmed the raw
`resource: String` crosses all four layers untouched and is only parsed (and panics) at QEMU-emit
time via `split_once('-').expect(...)`.

Asked: should this become a typed enum (`BusPort` vs `VendorProduct`) parsed once at import time?
User selected: **Yes, typed enum parsed at import time** (locked as D-01).

**Round 2 — SCSI controller type representation**

Explored `src/runtime/devices/pvscsi.rs` (single hardcoded `PvScsi` struct/builder implementing
Pci/Pcie/Isa device traits), `src/config/ezkvm/schema/pcie.rs` (`PcieDeviceTypeSchema::PvScsi` unit
variant), `src/config/proxmox/conf.rs` (`scsihw` parsed but unused), `src/config/proxmox/importer.rs`
(hardcoded `PvScsiBuilder` usage).

Raised the real-world nuance that `virtio-scsi-single` is structurally different from
`pvscsi`/`virtio-scsi-pci` (one controller per disk vs one shared controller for the whole VM) and
asked how to handle it.

User's response (verbatim insight): the current one-controller-for-the-whole-VM model is
architecturally flawed — a SCSI controller is fundamentally "a Pci/Pcie/Isa device that adds a scsi
bus to the vm," and the model should allow multiple controller instances. Proposed:
- A generalized `GenericScsiController` (name TBD) parameterized by controller type (PvScsi /
  VirtioScsi), reusing the existing shared-bus structure — locked as **D-02**.
- `virtio-scsi-single` as a separate device that is itself a Pci/Pcie/Isa device AND directly
  implements the storage device trait(s) (Ssd/Hdd/Odd), merging controller+single-disk into one
  device rather than a bus with one device hanging off it — captured as **D-03**, but marked
  **tentative**: the user stated they will follow up with more explicit instructions on this before
  implementation.

**Round 3 — scope clarifications**

- User confirmed: **no need to preserve backward compatibility** with existing ezkvm YAML files'
  current `PvScsi` device-type tag — locked as **D-04** (supersedes an earlier draft compatibility
  constraint written into CONTEXT.md before this clarification arrived).
- RawArgs smart re-injection remains out of scope, carried over from Phase 9 (D-05).
- Scope boundary: this phase covers Runtime/schema/importer/emitter changes only; Phase 9's
  round-trip integration tests remain Phase 9's job (D-06).

**Outcome (initial)**: `08.1-CONTEXT.md` written with D-01 through D-06. D-03 (virtio-scsi-single)
initially flagged as tentative, awaiting further user instruction.

**Round 4 — virtio-scsi-single follow-up (same session)**

User provided the promised follow-up immediately: model `virtio-scsi-single` as a Pci/Pcie/Isa
device that can *also* be an Ssd/Hdd/Odd device directly — no internal SCSI bus needed, since it
is inherently a single device by construction. This confirms and locks the direction already
drafted in D-03; updated `08.1-CONTEXT.md` to mark D-03 as **LOCKED** (removed tentative framing).

**Final outcome**: `08.1-CONTEXT.md` fully locked, D-01 through D-06 all final. Ready for
research/planning.

No git commit performed (user's standing no-auto-commit policy).
