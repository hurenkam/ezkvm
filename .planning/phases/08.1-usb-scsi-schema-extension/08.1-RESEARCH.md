## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01 (USB identity, typed + parsed early)**: Replace the untyped
  `UsbDeviceKind::HostPassthrough { resource: String }` (which crosses Proxmox import → Runtime →
  YAML → QEMU emitter as a raw string, parsed only at emit time — where it panics on the
  vendor:product-ID form) with a typed identity parsed once at the Proxmox-import boundary:
  `HostPassthrough { identity: UsbHostIdentity }` where `UsbHostIdentity` is an enum with two
  variants — bus-port (`bus`, `port`) and vendor:product-ID (`vendor`, `product`). Malformed input
  fails fast at import time with a typed error, not deep inside the emitter via `.expect()`.
  Applies to: Runtime (`src/runtime/devices/usb_generic.rs`), ezkvm YAML schema
  (`src/config/ezkvm/schema/usb.rs`), Proxmox importer (`src/config/proxmox/importer.rs`), QEMU
  emitter (`src/config/qemu/handlers/usb.rs`). **Research addendum: also applies to
  `src/config/ezkvm/runtime/parser.rs`, `src/config/ezkvm/runtime/builder.rs`, and
  `src/runtime/q35.rs` — three call sites not named in the original decision text; see Pitfall 1.**

- **D-02 (SCSI controller, generalized shared-bus controller)**: The current model — a single
  `PvScsi` struct hardcoded as the one-and-only SCSI controller for the whole VM — is
  architecturally wrong; a SCSI controller is fundamentally "a Pci/Pcie/Isa device that adds a
  SCSI bus to the VM," and the model must support **multiple controller instances** (the PCIe/PCI/
  ISA buses are already address-keyed collections, so this is natural, not a big structural
  change). Generalize `PvScsi` into a `GenericScsiController` (name TBD at planning time) that is
  parameterized by a `controller_type` field (e.g. `ScsiControllerType::PvScsi` |
  `::VirtioScsiPci`) and otherwise keeps today's shared-bus behavior (a
  `HashMap<ScsiAddress, Arc<dyn ScsiDevice>>` of attached disks). Both `pvscsi` and
  `virtio-scsi-pci` map onto this one generalized type — they differ only in the emitted QEMU
  device string, not in structural behavior. **Research addendum: an existing `bus`-keyed grouping
  mechanism in `builder.rs` (`PvScsiControllerSpec`/`pvsci_by_bus`) already supports multiple
  controller instances in the schema→Runtime direction — extend it, don't replace it. The
  Runtime→schema direction (`parser.rs`) and the QEMU emitter (`emit_pvscsi`/`emit_scsi_storage`)
  do NOT yet support multiple instances (hardcoded `Some(0)`/`scsihw0` labels) — see Pitfall 2.**

- **D-03 (virtio-scsi-single, separate merged device — LOCKED)**:
  `virtio-scsi-single` is NOT a shared-bus controller in real Proxmox/QEMU semantics — Proxmox
  creates one dedicated virtio-scsi controller instance *per disk* (for iothread/performance
  isolation). Confirmed direction: model it as a Pci/Pcie/Isa device that can *also* be an
  Ssd/Hdd/Odd device directly — i.e. the device itself implements both the bus-attachable
  controller trait(s) and the storage-device trait(s) — so it does not need its own internal SCSI
  bus (`HashMap<ScsiAddress, Arc<dyn ScsiDevice>>`) at all; it is inherently single-device by
  construction. One instance is created per Proxmox `scsiN` entry when `scsihw:
  virtio-scsi-single`. **Research addendum: this pattern (one Runtime struct implementing both a
  bus-attach trait and a storage-device trait) already has a working precedent in this codebase —
  `Ssd`/`Hdd`/`Cdrom` already implement `IdeDevice`+`SataDevice`+`ScsiDevice`+`StorageDevice`
  simultaneously (see Pattern 3). D-03 is architecturally consistent with existing code, not a new
  pattern.**

- **D-04 (no backward-compatibility constraint)**: Explicitly no need to preserve
  deserialization compatibility with existing ezkvm YAML files' current bare `PvScsi` device-type
  tag. The schema/type changes for D-02/D-03 are free to change the on-disk YAML shape for SCSI
  controllers without a compatibility shim or migration path.

- **D-05 (RawArgs smart re-injection stays out of scope)**: Carried over from Phase 9's discussion
  — recognizing RawArgs tokens that are properly supported elsewhere in Runtime/ezkvm and
  re-injecting them on export is explicitly deferred to a future phase. Not touched here.

- **D-06 (scope boundary)**: This phase covers Runtime, ezkvm YAML schema, Proxmox importer, and
  QEMU emitter changes for USB identity (D-01) and SCSI controller type (D-02/D-03). It does NOT
  redo Phase 9's round-trip integration tests — those remain Phase 9's responsibility once this
  phase lands. This phase's own tests are unit/structural-level (schema round-trip, importer
  mapping, emitter output), consistent with the project's existing no-real-QEMU-execution policy
  for pre-Phase-10 work.

## Summary

This phase touches far more call sites than the CONTEXT.md's headline file list suggests. `PvScsi`
and `UsbDeviceKind::HostPassthrough` are not confined to the four files named in D-01/D-02 —
they also thread through a **fifth layer** not mentioned in CONTEXT.md: `src/config/ezkvm/runtime/parser.rs`
(Runtime → ezkvm YAML, ~1000 lines) and `src/config/ezkvm/runtime/builder.rs` (ezkvm YAML → Runtime,
~706 lines), plus `src/runtime/q35.rs`'s `Display` formatting dispatch. Every one of `PciBusDeviceKind`,
`PcieBusDeviceKind`, and `IsaBusDeviceKind` is matched exhaustively in 5-6 separate places; adding a
new enum variant (or changing `PvScsi`'s shape) is a compile-error-driven ripple through all of them —
which is good (the compiler enforces completeness) but means the planner must budget tasks for each
site, not just the four named in CONTEXT.md.

Two structural discoveries materially de-risk D-02:
1. **The ezkvm-YAML-schema→Runtime direction (`builder.rs`) already has a `bus`-keyed grouping
   mechanism** (`BTreeMap<u8, PvScsiControllerSpec>`) that lets multiple SCSI-controller instances
   exist in the YAML today — `ScsiDeviceSchema.bus` and `PcieDeviceTypeSchema::PvScsi`'s own `bus`
   field are already independent per-entry tags used purely to correlate a disk with "its" controller.
   D-02's `controller_type` field is a small, natural addition to this existing mechanism, not a new
   one.
2. **The Runtime→ezkvm-YAML direction (`parser.rs`) does NOT yet support multiple controllers** — it
   hardcodes `Some(0)` as the bus tag for every `PvScsi` device found on `pcie_bus`, and only visits
   `pcie_bus` for `PvScsi` (the `pci_bus` loop errors out on any non-`GenericPci` device kind,
   meaning **`PvScsi` on the legacy PCI bus, and the entire ISA-bus `PvScsi` impl, are currently
   unreachable/untested through the ezkvm YAML round trip** — they exist only as directly-constructed
   Runtime objects in unit tests). This asymmetry must be fixed as part of D-02, and the QEMU emitter
   itself (`emit_pvscsi`, `emit_scsi_storage`) currently **hardcodes `id=scsihw0`/`bus=scsihw0.0`
   labels globally**, not parameterized by controller instance — a second controller would collide on
   label names. Real-world corpus data (see below) confirms Proxmox's `scsihw` is a single
   whole-VM setting (never mixed), so the *practical* need for N *shared-bus* controller instances is
   low, but D-03's `virtio-scsi-single` genuinely needs N *merged-device* instances (one per disk),
   which hits this exact same global-label collision unless addressed.

**Primary recommendation:** Implement D-01 (typed `UsbHostIdentity`) and D-02/D-03 (SCSI controller
model split) as described, but explicitly scope tasks to touch all 5 layers (Runtime types, ezkvm
schema, `parser.rs`, `builder.rs`, `importer.rs`, QEMU handlers `pci.rs`/`pcie.rs`/`usb.rs`), and add a
new task specifically for **label-collision-proofing** the QEMU emitter (`scsihw{N}`/`drive-scsi{N}-{target}`-
style naming) before D-03's per-disk `virtio-scsi-single` instances can safely coexist with each other
in one VM (real corpus data — zbp-server-mh2/301 — has 4 `scsi0..3` disks all under one
`virtio-scsi-single` declaration, meaning 4 separate merged-device instances in the same VM, today's
single hardcoded `scsihw0`/`drive-scsiN` naming already happens to avoid `id=scsihwN` collision only
because there's currently exactly one call site producing exactly one `id=scsihw0` per VM — under D-03
this becomes N call sites and must produce N distinct ids).

### Pattern 1: Parse-once-at-boundary, typed thereafter (D-01)
**What:** Proxmox's `usbN: host=<value>` is captured as a raw `String` by `parse_usb_raw` (already
distinguishes nothing — just extracts the `host=` sub-option value verbatim,
`config/proxmox/parser.rs:159-170`, confirmed by its own tests `test_parse_usb_raw_port` /
`test_parse_usb_raw_vid_pid`). The typed split into `UsbHostIdentity::BusPort{bus,port}` vs
`UsbHostIdentity::VendorProduct{vendor,product}` must happen in `ProxmoxImporter::into_runtime()`'s
usb loop (`config/proxmox/importer.rs:118-125`), not in `conf.rs`/`parser.rs` (those layers correctly
stay "raw string" per the existing division of labor — `conf.rs` does no interpretation, only key/value
splitting) and not in the QEMU emitter (today's bug: interpretation deferred all the way to emit time).
**When to use:** Any Proxmox field whose sub-syntax varies by real-world case and whose misinterpretation
should fail loudly and early rather than silently or via `.expect()` panic deep in the emitter.
**Example (existing project convention to follow, from `hostpci` import handling)**:
```rust
// Source: src/config/proxmox/importer.rs:92-107 (existing pattern, not USB — HostPci multifunction
// interpretation happens once at import time, not deferred to the emitter)
let x_vga = pci_conf.options.get("x-vga").map(|v| v == "1").unwrap_or(false);
let functions = if x_vga { vec![0u8, 1u8] } else { vec![0u8] };
let host_pci = HostPci::new(base_bdf, functions, pcie, x_vga, rombar, romfile);
```
Apply the same shape to USB: interpret `usb_conf.host` once, store `UsbHostIdentity`, and propagate a
typed error (`ProxmoxImportError` variant) if the string matches neither known form — this replaces
today's `.expect()`-panic-at-emit-time failure mode with a typed, at-import-time failure, consistent
with `RUNT-09`'s "thiserror from day one" project decision.

### Pattern 2: `bus`-keyed grouping already exists for multi-controller SCSI (D-02)
**What:** `config/ezkvm/runtime/builder.rs`'s `PvScsiControllerSpec` (line 31) and the
`BTreeMap<u8, PvScsiControllerSpec>` (`pvsci_by_bus`, line 119) already group scsi disks by a `bus: u8`
tag independent of PCIe address — `match_scsi_device` (line 383) does
`pvsci_by_bus.entry(bus).or_default().scsi_disks.push(...)` and `match_pcie_device`'s `PvScsi` arm
(line 414) does `pvsci_by_bus.entry(bus).or_default()` to record the PCIe slot for that same bus tag.
**When to use:** D-02's `controller_type` field should be added to `PvScsiControllerSpec` (read from
the `ScsiDeviceSchema`/`PcieDeviceTypeSchema::ScsiController` entries sharing that `bus` tag — all
disks under one `bus` value share one controller type, naturally, since Proxmox's `scsihw` is a single
whole-VM setting per corpus evidence below) rather than inventing a new grouping mechanism.
**Example:**
```rust
// Source: src/config/ezkvm/runtime/builder.rs:31-34 (existing, to extend)
#[derive(Default)]
struct PvScsiControllerSpec {
    pcie_address: Option<PcieAddress>,
    scsi_disks: Vec<(ScsiAddress, StorageKind, String)>,
    // ADD: controller_type: Option<ScsiControllerType>,
}
```

### Pattern 3: Multi-trait storage device (precedent for D-03's merged device)
**What:** `Ssd`/`Hdd`/`Cdrom` (`src/runtime/storage.rs:24-125`) already implement THREE bus-attachment
traits simultaneously (`IdeDevice`, `SataDevice`, `ScsiDevice`) plus `StorageDevice`. This is the exact
precedent D-03 needs: a single Runtime struct implementing multiple device-role traits at once is
already an established, working pattern in this codebase — D-03's `virtio-scsi-single` merged device
implementing `PciDevice`/`PcieDevice`/`IsaDevice` (controller role) AND the storage trait (disk role)
is architecturally consistent with existing code, not a new pattern.
**Example:**
```rust
// Source: src/runtime/storage.rs:59-63, 65-73
impl ScsiDevice for Ssd {
    fn as_any(&self) -> &dyn std::any::Any { self }
}
impl StorageDevice for Ssd {
    fn storage_options(&self) -> StorageOptions {
        StorageOptions { device_type: StorageDeviceType::Ssd, read_only: false, cache_mode: None }
    }
}
```

### Anti-Patterns to Avoid
- **Re-parsing `resource: String` at emit time:** The exact bug being fixed (D-01) — never defer
  interpretation of an ambiguous-syntax field past the import boundary.
- **Adding a 4th `ScsiControllerType` variant for `virtio-scsi-single`:** Explicitly rejected by D-03
  (LOCKED) — `virtio-scsi-single` is never a shared-bus controller type; it is always the separate
  merged-device type. Do not conflate the two.
- **Hardcoding controller-instance-0 assumptions in the QEMU emitter:** `emit_pvscsi`
  (`handlers/pcie.rs:65`) hardcodes `"-device pvscsi,id=scsihw0,bus=pci.0,addr=0x5"` and
  `emit_scsi_storage` (`handlers/storage.rs:22`) hardcodes `bus=scsihw0.0`/`drive-scsi{target}` — both
  assume exactly one controller instance exists in the whole VM. D-03's per-disk merged devices break
  this assumption the moment a `virtio-scsi-single` VM has more than one disk (real corpus data: every
  `virtio-scsi-single` corpus VM has ≥1 disk, several have 2-4 — see zbp-server-mh2/301 with 4).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| USB vendor:product-ID vs bus-port disambiguation | A bespoke regex or ad-hoc string-splitting scattered across layers | One `UsbHostIdentity::parse(&str) -> Result<Self, _>` function called once at import time (D-01) | Single source of truth; every downstream layer (Runtime/YAML/emitter) works with the typed enum, never re-parses |
| Multi-controller SCSI grouping | A new custom indexing scheme | Reuse the existing `bus: u8` tag + `BTreeMap` grouping already in `builder.rs`'s `PvScsiControllerSpec`/`pvsci_by_bus` (Pattern 2) | Already proven, already tested via existing `bus` field; extending it is strictly additive |
| Merged controller+disk device (`virtio-scsi-single`) | A special-cased `if scsihw == "virtio-scsi-single"` branch scattered through every handler | A genuine new Runtime type implementing both bus-attach and storage-device traits (D-03, Pattern 3) | Consistent with `Ssd`/`Hdd`/`Cdrom`'s existing multi-trait-impl precedent; keeps `device_kind()` dispatch exhaustive and compiler-checked rather than string-matched |

**Key insight:** This codebase already has the two structural patterns (bus-tag grouping,
multi-trait storage devices) needed for D-02/D-03 — the phase is mostly "extend existing patterns
consistently across 5 layers," not "invent new architecture."

## Common Pitfalls

### Pitfall 1: `PvScsi`/`UsbDeviceKind::HostPassthrough` call sites span 5 layers, not the 4 named in CONTEXT.md
**What goes wrong:** CONTEXT.md's "Applies to" lists name `usb_generic.rs`, `schema/usb.rs`,
`importer.rs`, `handlers/usb.rs` for D-01, and `pvscsi.rs`, `schema/pcie.rs`, `conf.rs`,
`importer.rs`, `handlers/pci.rs`, `handlers/pcie.rs` for D-02. Missing from both lists:
`config/ezkvm/runtime/parser.rs` (Runtime→YAML, exhaustively matches `PcieBusDeviceKind`/
`PciBusDeviceKind`/`UsbBusDeviceKind` three separate times) and `config/ezkvm/runtime/builder.rs`
(YAML→Runtime, same three enums matched again) and `runtime/q35.rs` (Display formatting, matches
`PcieBusDeviceKind`/`PciBusDeviceKind`/`UsbBusDeviceKind` a THIRD time for pretty-printing). A plan
that only touches the 4/7 named files will fail to compile (exhaustive match errors) the moment the
enum variants change.
**Why it happens:** CONTEXT.md was written during a discussion focused on the emitter-level bug and the
Runtime/schema-level fix, and didn't enumerate the intermediate YAML-schema conversion layer
(`config/ezkvm/runtime/{parser,builder}.rs`) which is architecturally separate from
`config/ezkvm/schema/*.rs` (the schema type *definitions*) — a subtlety easy to miss.
**How to avoid:** Plan explicit tasks for `parser.rs` (3 loops: pcie ~L169, pci ~L295, usb ~L349),
`builder.rs` (3 match functions: `match_usb_device` ~L312, `match_scsi_device` ~L383,
`match_pcie_device` ~L406, plus `match_pci_device` ~L336 if a legacy-PCI-bus SCSI schema variant is
added), and `runtime/q35.rs` (`format_pcie_device` ~L166, `format_pci_device` ~L207,
`format_usb_device` ~L220). Rust's exhaustive-match compiler errors will catch any missed site during
implementation (a safety net, but still costs a wasted task-planning cycle if not anticipated).
**Warning signs:** `cargo build` errors like "non-exhaustive patterns" pointing at any of the 3
`format_*_device` functions in `q35.rs`, or at `parser.rs`/`builder.rs` match arms, after changing
`PciBusDeviceKind`/`PcieBusDeviceKind`/`IsaBusDeviceKind`/`UsbDeviceKind` variant shapes.

### Pitfall 2: `emit_pvscsi`/`emit_scsi_storage` hardcode single-controller-instance labels
**What goes wrong:** `handlers/pcie.rs:65` (`emit_pvscsi`) emits a literal
`"-device pvscsi,id=scsihw0,bus=pci.0,addr=0x5"` string — `scsihw0` and `addr=0x5` are NOT derived
from any per-instance counter or address; they are constants. `handlers/storage.rs:22`
(`emit_scsi_storage`) similarly hardcodes `bus=scsihw0.0` and `id=drive-scsi{target}`/`id=scsi{target}`
— using only the disk's `target` (0-3 typically), never a controller-instance identifier. Today this is
harmless because exactly one `PvScsi` instance exists per VM. Under D-03, `virtio-scsi-single` produces
N per-disk merged-device instances in ONE VM (real corpus proof: zbp-server-mh2/301 has 4 `scsiN` disks
under one `scsihw: virtio-scsi-single`) — if each merged device's emission reuses `id=scsihw0` (or any
constant), all N QEMU `-device` lines collide on `id=`, producing an invalid (and likely silently
broken, not compile-time-caught) QEMU commandline.
**Why it happens:** The original Phase 7 design only ever needed one controller instance (Proxmox's
single global `scsihw` setting always maps to exactly one shared bus in the old `PvScsi`-only model);
nothing in that phase's scope anticipated N controller instances.
**How to avoid:** Parameterize `emit_pvscsi`(-equivalent) and `emit_scsi_storage` by a controller
instance identifier — natural candidates: the PCIe/PCI/ISA slot address already carried alongside each
controller (`PcieAddress`/`PciAddress`/`IsaAddress`), or the Proxmox `scsiN` index itself for
`virtio-scsi-single` (since each merged device corresponds 1:1 to one original `scsiN` disk key, its own
index is a natural, collision-free id — e.g. `id=scsihw{N}`, `drive-scsi{N}`). The planner must decide
which; either works, but it must NOT remain a hardcoded literal once >1 controller instance is possible.
Note this changes `emit_scsi_storage`'s signature (currently takes `target: u8` alone) — an additive,
not breaking, change if the new parameter has a sensible default matching today's single-controller
behavior for existing tests.
**Warning signs:** Two or more `-device ...,id=scsihw0` (or `id=scsi{N}`) lines in one emitted
commandline; QEMU itself would reject this at actual boot time (duplicate device id), but this
project's own "no real-QEMU execution before Phase 10" policy means a structural/unit test must catch
this instead (assert unique `id=` tokens across all emitted `-device` lines for a multi-disk
`virtio-scsi-single` scenario).

### Pitfall 3: `PvScsi` (SCSI controller) has NO `PciDeviceTypeSchema` variant in the ezkvm YAML schema today
**What goes wrong:** `runtime/pci.rs`'s `PciBusDeviceKind::PvScsi` and `handlers/pci.rs`'s dispatch arm
both exist and are exercised by direct-Runtime-construction unit tests
(`test_07_03_pvscsi_on_pci_bus_reuses_emit_pvscsi`), but `config/ezkvm/schema/pci.rs`'s
`PciDeviceTypeSchema` enum has only `NetworkController | QxlGpu | Ac97 | HostPci` — **no `PvScsi`
variant at all**. `config/ezkvm/runtime/parser.rs`'s `pci_entries` loop (~L295-315) actively
**returns an error** (`YamlRuntimeError::UnsupportedPcieDevice`) for any `pci_device.device_kind() !=
PciBusDeviceKind::GenericPci` — meaning a `GenericScsiController` placed on the legacy PCI bus can be
constructed and emitted to QEMU today, but CANNOT round-trip through the ezkvm YAML format at all.
Similarly, there is no ISA-bus schema file (`config/ezkvm/schema/isa.rs` does not exist) and no ISA QEMU
handler (`config/qemu/handlers/isa.rs` does not exist) — `IsaBusDeviceKind::PvScsi` and `IsaDevice for
PvScsi` are Runtime-level-only, entirely disconnected from both the YAML schema and the QEMU emitter.
Grep confirms: `Q35ChipsetBuilder` (`runtime/q35.rs`) has no `isa_bus` field at all — the ISA bus isn't
wired into the chipset builder either.
**Why it happens:** Likely vestigial from an early multi-bus design sketch; only the PCIe path was ever
fully wired end-to-end (Proxmox always places its `scsihw` controller on a PCIe slot in this project's
model, per `importer.rs:49`'s hardcoded `PcieAddress::new(16, 0)`).
**How to avoid:** The planner should explicitly scope D-02/D-03 to the PCIe bus path only (matching
real-world Proxmox usage — no corpus file needs a legacy-PCI or ISA SCSI controller) and treat the
existing `PciDevice`/`IsaDevice` trait impls for the generalized type as either (a) removed if truly
unused/unreachable, or (b) explicitly kept but documented as "constructible in Runtime, not
YAML-round-trippable, not QEMU-reachable via normal import" — a decision CONTEXT.md does not make and
the planner must resolve. Recommendation: keep the PCI/ISA trait impls (matches the "PCIe/PCI/ISA buses
already support multiple instances" architecture point in D-02) since removing them is unnecessary
churn, but do NOT expand this phase's scope to also wire up a `PciDeviceTypeSchema::ScsiController`
variant or an ISA schema/handler — that is a separate, un-requested feature; flag as an Open Question
for planner/user sign-off rather than silently doing (or silently skipping) the extra work.
**Warning signs:** A plan task that tries to add `PciDeviceTypeSchema::ScsiController` "for
completeness" — this is scope creep beyond D-02/D-03's literal text unless the user confirms it's
wanted.

### Pitfall 4: `scsihw` field has a parsing subtlety — must be checked BEFORE `scsiN` prefix matching
**What goes wrong:** `config/proxmox/conf.rs:116-118`'s comment ("scsihw must be checked BEFORE any
starts_with('scsi') prefix") flags that `scsihw` itself starts with `"scsi"` — a naive prefix-strip
parser (stripping trailing digits from `scsiN` keys) would misparse `scsihw` as `scsi` + suffix `"hw"`
(non-numeric, so likely already guarded, but worth explicit verification) if the field-dispatch order
in `conf.rs` changes. This ordering constraint already exists and is respected in the current code
(this is not a new bug) — flagged here only because D-02's importer work touches the same
`self.vm_conf.scsihw` field and adjacent `scsiN` loop, so any refactor of `importer.rs`'s scsi-handling
section must preserve `conf.rs`'s existing correct behavior, not `conf.rs`'s ordering itself (which is
already correct and does not need to change for this phase).
**Why it happens:** Proxmox's own key-naming collision (`scsihw` vs `scsiN`), already correctly handled
upstream in the parser.
**How to avoid:** No new work needed in `conf.rs` — `ProxmoxVmConf.scsihw: Option<String>` is already
correctly populated. D-02's importer work only needs to *read* `self.vm_conf.scsihw.as_deref()` and
match on `"pvscsi"` / `"virtio-scsi-pci"` / `"virtio-scsi-single"` (with a sensible default — Proxmox's
own default is `"lsi"` for legacy VMs, but no corpus file omits `scsihw` when it has `scsiN` disks,
except felucia/108.conf's convention of always specifying `pvscsi` explicitly — confirm default-handling
behavior with the user/planner if a corpus edge case surfaces, but treat "missing `scsihw` + present
`scsiN` disks" as a possible open question, not a silent default choice).
**Warning signs:** A disk imported under `scsihw: unset` silently becoming `PvScsi`-shaped without an
explicit decision recorded — should instead be an explicit fallback documented in code comments/tests.

### Pitfall 5: Real corpus data has multiple `scsihw:`/`scsiN:` lines per `.conf` file — these are snapshot sections, already handled
**What goes wrong:** `grep -n scsihw` on several corpus `.conf` files (e.g. `coruscant/103.conf`,
`coruscant/105.conf`, `coruscant/2000.conf`) shows the same `scsihw`/`scsiN` lines repeated 3-5 times
within one file. A naive reader might assume this means "one VM has multiple simultaneous
`scsihw` declarations" (a genuine ambiguity to resolve) — it does NOT; per this project's own
already-locked "Snapshot sections must be split first" decision (STATE.md Accumulated Context), these
are Proxmox named-snapshot sections (`[snapshot_name]` blocks), each carrying its own point-in-time
config copy, and `conf.rs`'s existing snapshot-splitting logic already discards all but the active
(unnamed) section before any field parsing happens.
**Why it happens:** Proxmox `.conf` files accumulate one full config copy per named snapshot; this is
normal, expected file shape, not a data-quality issue.
**How to avoid:** When writing structural/unit tests referencing corpus `scsihw` values, use only the
FIRST occurrence in each file (the active/current config) — already how the existing parser behaves;
no new work needed here, just an awareness note for whoever writes D-02's importer tests against real
corpus files.
**Warning signs:** A test asserting "scsihw appears N times" instead of "the active section's scsihw is
X" — the former is describing snapshot-section noise, not real controller-type ambiguity.

## Open Questions

1. **Should `GenericScsiController`/the merged `virtio-scsi-single` device also get a `PciDeviceTypeSchema`
   (legacy PCI bus) and/or ISA-bus schema+handler, given `PciBusDeviceKind::PvScsi` and
   `IsaBusDeviceKind::PvScsi` already exist in Runtime but have NO schema/handler wiring today
   (Pitfall 3)?**
   - What we know: Real corpus data never needs a legacy-PCI or ISA SCSI controller (Proxmox always
     uses a PCIe slot in this project's importer, `PcieAddress::new(16, 0)` hardcoded).
   - What's unclear: Whether the existing PCI/ISA trait impls are meant to stay as forward-looking
     architecture (per D-02's own framing — "PCIe/PCI/ISA buses already support multiple instances")
     or whether they're dead code that should be pruned as part of this phase's cleanup.
   - Recommendation: Keep the trait impls (cheap to maintain, matches stated architecture intent), do
     NOT add new PCI/ISA schema+handler wiring in this phase (no corpus need, avoids scope creep beyond
     D-01/D-02/D-03's literal text) — but surface this explicitly to the user/planner rather than
     silently deciding either way, since CONTEXT.md doesn't address it.

2. **What is the exact controller-instance-uniqueness label scheme for D-03's per-disk merged
   devices (Pitfall 2)?**
   - What we know: Today's `emit_pvscsi`/`emit_scsi_storage` hardcode `scsihw0`/`drive-scsi{target}`
     assuming exactly one controller; this breaks under D-03 with N merged-device instances in one VM.
   - What's unclear: Whether to key the new label on the Proxmox `scsiN` index (simplest, matches 1:1
     disk-to-controller correspondence for `virtio-scsi-single`) or on the PCIe/PCI/ISA slot address
     (more general, works for hypothetical future multi-shared-controller scenarios too).
   - Recommendation: Use the Proxmox `scsiN` index as the label key for `virtio-scsi-single` devices
     specifically (matches real-world 1:1 correspondence, simplest to implement and test); the shared
     `GenericScsiController` (pvscsi/virtio-scsi-pci) can keep today's `scsihw0`/target-only scheme
     unchanged in the common case (exactly one shared controller per VM, as all corpus data shows) —
     but the emitter functions should still accept an explicit controller-id parameter rather than a
     hardcoded literal, so a second shared-controller-type instance (however unlikely in practice)
     doesn't silently collide either.

3. **Does `ProxmoxVmConf.scsihw` need a typed enum (`ScsiControllerType`) at the Proxmox-conf-parsing
   layer itself, or is `Option<String>` (today's shape) fine to keep at that layer, with typing only
   introduced at the Runtime-import boundary (mirroring D-01's "typed at import time, not before" data
   flow)?**
   - What we know: `conf.rs` currently stores `scsihw` as `Option<String>` (matches its role as a
     "parse structure, don't interpret semantics" layer, same division of labor as USB's `host` field).
   - What's unclear: Whether project convention prefers typing exactly at the import boundary (matching
     D-01's explicit design) or one layer earlier.
   - Recommendation: Keep `conf.rs`'s `scsihw: Option<String>` unchanged (consistent with the existing
     division of labor demonstrated by USB's `host: String` field in `ProxmoxUsbConf`) and introduce
     `ScsiControllerType` typing in `ProxmoxImporter::into_runtime()`'s scsi loop, exactly mirroring
     D-01's USB pattern — this keeps both phase's fixes architecturally symmetric.
