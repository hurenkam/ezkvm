<objective>
Build the phase's tracer slice: the smallest end-to-end path through every layer this phase
touches — packaging metadata, install-time scripts, FHS layout, and a real containerized QEMU
boot — proven on ONE target distro (`debian:bookworm`) before Plan 10-02 expands the same CI
workflow to all four required targets (D-08). Implements D-01 (cargo-deb), D-02 (no systemd
service — tmpfiles.d only), D-03 (dedicated `ezkvm` group, no libvirt dependency), D-04 (FHS
layout), D-07 (Cargo.toml-tracked version, `-1` Debian revision suffix), and the packaging-tooling
half of D-05/D-08 (single musl-static `.deb`, Docker+`/dev/kvm` verification).

This project has no existing `[package.metadata.deb]` config and no existing `.github/workflows/`
— both are genuinely new infrastructure, not an extension of prior-phase patterns (per
`10-RESEARCH.md`'s Summary and Wave 0 Gaps).

Purpose: Prove the packaging + real-QEMU-boot architecture works end-to-end on one target before
committing to the full 4-distro CI matrix, catching any architectural dead-end (e.g. a
`ResourceSchema` validation surprise, a wrong `Depends:` package name) after one target instead of
after four.
Output: A buildable, installable `.deb` with correct metadata and install-time scripts, plus a
GitHub Actions workflow that builds it and verifies a real `ezkvm start`/`status`/`stop`/`kill`/
`reset` lifecycle against real `qemu-system-x86_64` inside a `debian:bookworm` container.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `dpkg -i` install-time scripts (root) | `postinst`/`postrm` run as root at install/purge time — the only privileged code this phase introduces |
| `ezkvm` group membership → `/dev/kvm` + FHS dirs | Local users gain KVM + VM-config/state access once added to the group (D-03's explicit, accepted tradeoff) |
| CI runner `/dev/kvm` permission relaxation | `sudo chmod 666 /dev/kvm` loosens host device permissions for the duration of one throwaway CI job only |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-01 | Information Disclosure / Elevation of Privilege | `postinst`'s `/etc/ezkvm`, `/var/lib/ezkvm`, `debian/ezkvm.conf`'s `/run/ezkvm` permissions | high | mitigate | `0750`/`0770` group-`ezkvm`-restricted permissions via atomic `install -d`/tmpfiles.d, never world-readable/writable — per RESEARCH.md's Security Domain V4 guidance |
| T-10-02 | Tampering | `postinst`/`postrm` running as root at install time | medium | mitigate | `set -e`, atomic `install -d` (no TOCTOU mkdir+chmod gap), no interpolation of external/attacker-influenced input, idempotent guards (`getent group ezkvm \|\|`) |
| T-10-03 | Elevation of Privilege | `ezkvm` group grants `/dev/kvm` access | medium | accept | Explicit, already-locked D-03 tradeoff (same tradeoff Debian's own `kvm` group makes); documented in `debian/host.yaml.example`'s header comment so users understand the grant |
| T-10-04 | Elevation of Privilege | CI-only `sudo chmod 666 /dev/kvm` in the verify job | low | accept | Scoped to a single throwaway GitHub-hosted runner destroyed after the job; explicitly documented as NOT a pattern for real user machines |
| T-10-SC | Tampering | `cargo-deb`, `musl-tools`, `rustup` target installs | low | accept | All three already carry a HIGH-confidence Package Legitimacy Audit verdict ("Approved") in `10-RESEARCH.md`, verified live against crates.io/GitHub API this research cycle — no new unaudited package is introduced by this task |

</threat_model>
